## 2. 신용도 점수 시스템

### 2-1) 설계 철학

- 정답 시 획득, 오답 시 차감하는 **비대칭 배당형 구조** (Polymarket류 예측시장 원리 차용)
- 득표 비율(p)에 따라 보상/페널티가 달라짐 → 소수 의견 적중 시 큰 보상, 다수 의견 적중 시 작은 보상
- **50/50(반반)일 때 장기적으로 가장 안정적인 플러스**가 나도록 설계 → "진짜 고민되는 주제에 계속 참여하는 게 제일 이득"이 되도록 유도
- 압도적으로 쉬운 선택(다수 의견) 또는 극단적 언더독 몰빵 모두 장기적으로 파밍 이득이 없도록 설계 → 신용도 점수의 예측력 신뢰도 유지

### 2-2) 득표 비율 계산 (가상 시딩)

```
p = (내가 고른 쪽 실제 득표 + 5) / (전체 실제 득표 + 10)
```

- 참여자 수와 무관하게 **항상 이 공식 하나만 사용** (별도 조건 분기 없음)
- 가상의 유령 투표 10표(Yes 5 / No 5)를 미리 깔아두는 개념
- 참여자가 적을 때는 가상 표의 영향력이 커서 극단값(예: 1명 참여 시 p=100%) 방지
- 참여자가 많아질수록 가상 표의 영향력이 자동으로 옅어져 실제 비율에 수렴

| 실제 참여자 수 | 실제 득표 (Yes) | 계산되는 p |
| --- | --- | --- |
| 3명 | Yes 2, No 1 | 53.8% |
| 10명 | Yes 6, No 4 | 55.0% |
| 100명 | Yes 60, No 40 | 59.1% |
| 1,000명 | Yes 600, No 400 | 59.9% |

### 2-3) 점수 계산 공식

```
p = (내가 고른 쪽 득표 + 5) / (전체 득표 + 10)
bonus(p) = 2 × [1 - 4×(p - 0.5)²]

정답 시:  score = round(40×(1-p) + bonus(p))
오답 시:  score = round(-(40×p - bonus(p)))
```

### 2-4) 예상 점수표

| 득표비율(p) | 유형 | 정답 시 | 오답 시 | 장기 기댓값(p=실제확률 가정) |
| --- | --- | --- | --- | --- |
| 10% | 극단적 소수 | +36.7 | -3.3 | -2.7 |
| 20% | 소수 | +33.3 | -5.3 | -1.1 |
| 30% | 소수 | +29.7 | -10.3 | -0.4 |
| 40% | 약한 소수 | +25.8 | -14.9 | +0.7 |
| **50%** | **반반 (기준)** | **+22.0** | **-18.0** | **+2.0** |
| 60% | 약한 다수 | +17.7 | -21.7 | +1.9 |
| 70% | 다수 | +13.7 | -26.3 | +1.6 |
| 80% | 다수 | +9.3 | -30.7 | +1.0 |
| 90% | 압도적 다수 | +4.7 | -35.3 | +0.5 |

### 2-5) 누적 점수 하한선

```
if (누적 신용도 점수 < 0):
    누적 신용도 점수 = 0
```

티어표의 최저 티어 "언랭크: 0"과 정합성 유지.

### 2-6) 득표 비율 공개 시점

- **투표 완료 전**: 실시간 Yes/No 비율 비공개 (게이밍 방지 — 마감 직전 유리한 쪽으로 쏠리는 전략적 행동 차단)
- **투표 완료 직후**: 본인에게 즉시 실시간 비율 노출 (재미 요소 — "나만 소수였다" 같은 반응 유도, 바이럴 요소로 연결 가능)
- ⚠️ 친구와 UI 구현 관점에서 최종 상의 필요

### 2-7) 결과 무효 처리(Void) 규칙

결과 확정이 불가하거나 취소된 경우(예: 경기 우천 취소):

- 점수 변동 없음 (+0 / -0)
- 참여 기록은 로그에 남기되 "void" 상태로 별도 표시
- 연속 정답 스트릭(향후 뱃지 시스템용)에 영향 없음 — 끊지도, 이어지지도 않고 건너뜀

### 2-8) 보류/추후 결정 항목

| 항목 | 내용 | 결정 시점 |
| --- | --- | --- |
| 연승 배수 보너스 | 점수 자체에 곱해지는 연승 배수는 도입하지 않음. 대신 "X연속 정답 뱃지"로 전시성 보상만 우선 적용 | 추후 뱃지 시스템(Phase 3)에서 별도 설계 |
| 극단값(p→100%) 근접 시 0점 문제 | 가상 시딩 덕분에 순수 100%는 거의 발생하지 않을 것으로 예상 | 베타 데이터로 실제 근접 정도 확인 후 필요 시 최소 보상(+1) 검토 |
| 카테고리 편중도(파밍 패턴) | 상위 티어 유저가 특정 카테고리(날씨 등 쉬운 카테고리)에 몰리는지 여부 | Phase 3 데이터 분석 시 확인 |

## 3. 티어 시스템

| 다이아 | 400~499 |

- 각 구간 100점 단위로 균등 분할
- 누적 신용도 점수 기준 자동 산정

### 예상 도달 기간 (참고용 시뮬레이션)

- 가정: p=50% 근처 판당 평균 +2점, 주 35표(하루 5표) 참여 기준 → 주당 약 +70점
- ⚠️ 이론적 평균치이며, 베타 1~2주차 실측 데이터로 재조정 가능성 있음

| 티어 | 필요 점수 | 예상 도달 기간 |
| --- | --- | --- |
| 브론즈 | 1 | 첫 정답 즉시 |
| 실버 | 100 | 약 1.5주 |
| 골드 | 200 | 약 3주 |
| 플래티넘 | 300 | 약 4주 |
| 다이아 | 400 | 약 6주 |
| 마스터 | 500 | 약 7주 |

### 3-2) 강등 규칙

강등은 두 개의 층으로 구성됨: **① 점수 기반 자연 강등(전 티어 공통, 기본 동작)** + **② 다이아/마스터 전용 활동성 조건(추가 오버레이)**

**① 점수 기반 자연 강등 (기본 원칙, 상시 적용)**

```
티어는 항상 "현재 누적 점수"에 따라 실시간으로 결정됨
- 오답이 쌓여 누적 점수가 하위 구간으로 내려가면 → 자동으로 강등
- 다시 점수가 올라 상위 구간을 충족하면 → 자동으로 승급
```

점수 공식 자체가 정답 시 상승 / 오답 시 하락하는 구조이므로(양방향 변동), 티어가 이를 그대로 반영해 오르내리는 것이 기본 동작. 별도의 "강등 방지" 로직 불필요 — 점수 구간표를 그대로 따르면 됨.

**② 다이아 / 마스터 전용 추가 조건 (활동성 유지)**

```
- 매주 일요일 자정 체크
- 해당 주(월~일) 투표 "참여 횟수"가 5회 미만이면
  → 그 주의 누적 점수가 여전히 다이아/마스터 구간이더라도, 점수와 무관하게 한 단계 추가 강등
  → 누적 점수는 변동 없음 (점수는 그대로, 티어 표시만 하강)
- 다음 주 참여 횟수 ≥ 5회를 채우면, 그 시점 누적 점수 기준으로 티어 재확인 → 복귀
```

**①과 ②의 관계**: ①은 모든 티어에 항상 적용되는 기본 동작(점수가 떨어지면 강등되는 당연한 원리)이고, ②는 다이아/마스터에만 추가로 얹히는 별도 조건.

**설계 근거**

- ①이 필요한 이유: 점수가 위아래로 움직이는 구조인데 티어가 한쪽으로만 움직이면 점수-티어 불일치가 생김.
- ②에서 정답/오답 여부와 무관하게 "참여 횟수"만 보는 이유: 정확도는 이미 ①(누적 점수)에 반영되어 있으므로, ②는 순수하게 "활동성"이라는 별개의 축만 체크.
- ②에서 순득점 대신 참여 횟수를 쓰는 이유: 경제/정치처럼 결과 확정이 몇 주 지연되는 카테고리가 있어, 순득점 집계 시 투표 시점과 정산 시점이 어긋나는 문제 발생. 참여 횟수는 정산 지연과 무관하게 집계 가능.
- ②가 "표시만 강등"인 이유: 활동을 안 했다고 누적 점수까지 깎으면 유저 신뢰 저해 우려.

### 3-3) 개발 전달 스펙 요약 (최신)

```
[티어 산정 — 기본, 상시 실시간 반영]
- tier 필드는 누적 점수(credibility_score)와 별도 컬럼으로 저장
- 점수 변동(정답/오답 정산) 시마다 credibility_score 기준으로 tier 재계산
- 상위 구간 진입 시 승급, 하위 구간으로 떨어지면 강등 — 양방향 모두 자동 반영

[강등 체크 — 다이아/마스터 한정, 위 기본 로직에 추가되는 오버레이]
- 배치 주기: 매주 일요일 자정 (KST)
- 조건: 해당 유저의 주간(월~일) 투표 참여 횟수 < 5
- 집계 기준: 투표 행위(vote) 이벤트의 timestamp 기준
  (결과 확정 timestamp 아님 — 정산 지연 카테고리와 무관하게 정확히 집계)
- 카운트 대상: 정답/오답/무효(void) 관계없이 투표 행위 자체만 카운트
- 조건 미충족 시: credibility_score는 유지, tier 필드만 한 단계 하강
- 재상승 조건: 다음 주 이후 참여 횟수 ≥ 5 이면서, credibility_score가 해당 구간 재충족 시 자동 복귀
```

### 3-4) 열린 질문 (베타 진행하며 재검토)

| 항목 | 내용 |
| --- | --- |
| 도달 속도 재조정 | 예상 시뮬레이션(주 70점)이 실제 지인 베타 참여 패턴과 다를 경우 구간 값 재보정 |

| **공유 클릭** | user_id, 공유채널, 클릭시각 |  |

### 4-1) 결과 확정 & 점수 정산 처리 흐름

```
[투표 진행중]
      ↓ 마감시각 도달 (자동)
[결과 대기]
      ↓ 관리자가 정답(Yes/No/무효) 선택 (수동, API 호출)
[정산 처리 — DB 트랜잭션]
      BEGIN TRANSACTION
        1. topic 상태를 "확정"으로 변경
        2. 참여자 전원의 p 계산 → 점수 계산 → credibility_score 갱신
        3. tier 재계산
        4. "점수 정산" 이벤트 로그 기록 (참여자 수만큼)
      전부 성공 시 COMMIT / 하나라도 실패 시 ROLLBACK
      ↓
[정산 완료]
```

- 현재 규모(지인 베타)에서는 큐 기반 비동기 처리 불필요 — 트랜잭션 내 동기 처리로 충분
- 참여자 규모가 수천 명 이상으로 커질 경우, 큐(Bull 등) 기반 비동기 처리로 전환 검토 (지금은 해당 없음)

## 5. 관리자 페이지 스펙

> `schema_8.sql`에 추가된 관리자 지원 스키마(role / activity_suppressed / confirmed_by 컬럼, 4종 프로시저) 기준으로 정리.

### 5-1) 권한 체계

- `users.role`: `'user'` \| `'admin'` — 관리자 페이지 접근 및 관리자 전용 API 호출 권한 체크에 사용
- 권한 부여/해제는 관리자만 실행 가능 (실행자 role 검증)
- **마지막 남은 관리자는 강등 불가** — 관리자가 0명이 되어 아무도 관리자 페이지에 못 들어가는 상황 방지

### 5-2) 결과 확정 플로우 (4-1 보강)

```
[투표 진행중: open]
      ↓ 마감시각 도달 (자동, 배치)
[결과 대기: pending_result]
      ↓ 관리자가 "Yes/No/무효" 버튼 클릭 (수동)
[정산 처리 — 단일 트랜잭션]
      1. 마감 시점 득표수 확정 → topics 반영, confirmed_by에 관리자 user_id 기록
      2. (void가 아니면) 참여자 전원 p값·점수변동·정산후점수 계산
      3. score_settlements 저장, credibility_score 갱신
      4. tier 재계산 → 실제로 바뀐 유저만 tier_changes 로그
      전부 성공 시 COMMIT / 하나라도 실패 시 ROLLBACK
      ↓
[확정: confirmed / void]
```

- `confirmed_by`로 "누가 이 결과를 확정했는지" 기록 → 오확정 발생 시 책임 소재 추적
- **안전장치**: 이미 `confirmed`/`void` 상태인 주제는 재확정 불가 (중복 정산으로 점수가 두 배 계산되는 것을 방지) — 정정하려면 5-3 절차를 먼저 거쳐야 함

### 5-3) 오확정 정정

관리자가 잘못된 답으로 확정한 것을 발견했을 때 사용.

- 대상: `confirmed` 또는 `void` 상태 주제만 (아직 미확정이면 정정 대상 아님)
- 기존 정산 기록은 **삭제하지 않고** `is_reversed = 1`로만 표시 → 실수 기록도 감사(audit) 목적으로 영구 보존
- 영향받은 유저의 `credibility_score`는 남아있는(무효 아닌) 정산 기록만으로 **시간순 재생(replay)**하여 재계산 (0 하한선 동일 적용)
- 정정 후 주제는 `pending_result`로 되돌아가고, 올바른 정답으로 다시 확정하면 정상 재정산됨
- 재계산으로 실제 티어가 바뀐 유저는 `tier_changes`에 사유 `correction`으로 별도 기록 (자연 변동과 구분)

### 5-4) 주제 수정 규칙

| 조건 | 허용 범위 |
| --- | --- |
| `open` 상태 + 참여자 0명 | 카테고리/제목/설명/투표 시작·마감시각 전체 수정 가능 |
| 참여자 1명 이상 (상태 무관) | 마감시각 **연장만** 가능 (단축 불가) |

- 내용을 잠그는 이유: 이미 투표한 유저가 본 질문이 사후에 바뀌면 공정성 문제 발생

### 5-5) 활동성 강등 상태 표시

- `users.activity_suppressed = 1`이면 `credibility_score`가 다이아/마스터 기준(400+/500+)을 충족해도 **플래티넘까지만** 표시
- 다이아/마스터로의 복귀는 오직 주간 활동성 체크(3-2, 3-3)를 통해서만 가능 — 정답/오답에 의한 실시간 정산으로는 복귀되지 않음

### 5-6) 관리자 페이지 화면 ↔ 백엔드 매핑

| 화면/기능 | 백엔드 처리 |
| --- | --- |
| 주제 목록 (카테고리/상태/검색어 필터, 페이지네이션) | 조회 쿼리 |
| 주제 상세 + 실시간 Yes/No 득표 현황 | 조회 쿼리 |
| 결과 확정 (Yes/No/무효 버튼) | `sp_confirm_topic_result(topic_id, answer, admin_id)` |
| 오확정 정정 버튼 (confirmed/void 상태에만 노출) | `sp_correct_topic_result(topic_id)` |
| 주제 수정 (참여자 0명일 때만) | `sp_update_topic(...)` |
| 마감시각 연장 | `sp_extend_topic_deadline(topic_id, new_deadline)` |
| 유저 검색/상세 (닉네임·role·티어 필터, 정답률 등 통계) | 조회 쿼리 |
| 관리자 목록 조회 / 권한 부여·해제 | `sp_set_admin_role(target_user_id, new_role, actor_admin_id)` |
